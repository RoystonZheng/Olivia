# Olivia V1（第一期）执行计划

更新日期：2026-08-05

## 1. 仓库现状与结论

当前仓库只有 `.git`，没有提交、源码或全息界面原型。因此 V1 按从零开发处理，不需要先删除或改造全息原型。

已确认首台测试设备为 **HUAWEI Pura 90，HarmonyOS 6.1.1（API 24）**，主要测试城市为**北京**，仅作个人测试。V1 因此采用 HarmonyOS 原生应用，不开发 Android APK。

第一期只交付 M1～M3：

1. M1：华为端登录、可靠唤醒入口、语音对话、结构化偏好云端保存。
2. M2：完成“中午吃什么 → 选择口味 → 返回 3～5 家 → 换口味/预算/一家”的闭环。
3. M3：对选中商家发起电话，创建任务，并在通话后记录用户确认的结果。

M4 活动推荐、M5 订票/外卖/消息、付款、全息界面和全自动后台 agent 都不进入本期。

## 2. 三个必须先接受的产品边界

### 2.1 “唤醒”先做可靠入口，不承诺全天候热词监听

第一版目标是先让核心功能作为一个普通程序稳定运行，不处理耳机品类和长期后台待命。V1 的入口按以下优先级实现：

1. App 内点击“说话”后录入一句话；
2. App 内文字输入，作为语音或网络失败时的兜底；
3. 核心闭环稳定后，再验证桌面卡片、系统意图或热词唤醒；
4. 耳机按键与锁屏长期待命不进入本次原型验收。

“默认安静”的验收含义是：用户没有点击或输入时，不录音、不播报、不弹窗。全天锁屏热词待命属于后续增强项，不作为当前 V1 阻塞条件。

### 2.2 电话可以直接发起，但不能承诺替用户完整通话

V1 使用 HarmonyOS Telephony Kit 的拨打电话能力拉起系统电话流程。拨号前先创建任务，返回 App 后只追问一个问题：“打通了吗？”然后允许用户用语音或按钮记录“有位/没位/无人接/稍后再问”等结果。

V1 不录制运营商电话音频，不冒充用户，不承诺自动识别商家回答。自动代打与通话转写需要额外的系统权限、电话线路服务、合规审查，留到后续独立验证。

### 2.3 餐厅解释只使用有来源的数据，绝不让模型编造

高德 POI 接口可返回部分餐厅的距离、电话、评分、人均消费和特色标签，但不保证每家都有这些字段，也不提供稳定的逐条差评正文。V1 规则：

- 招牌菜：只展示 POI 返回的 `tag`/特色内容；缺失时显示“暂无可靠招牌菜数据”。
- 风险提示：由可验证字段生成，例如“价格信息缺失”“评分样本信息不足”“距离接近你的上限”“电话缺失”；没有评论数据时明确显示“暂无可验证差评摘要”。
- 不抓取大众点评等平台页面，不伪造差评。
- 后续若取得合法评论数据授权，再增加真正的评论风险摘要。

## 3. 推荐技术方案

### 手机端

- ArkTS + ArkUI，构建 HarmonyOS 原生 HAP 应用，兼容目标设备 API 24。
- Location Kit 获取当前位置；Map Kit/Site 能力负责地点搜索或地图跳转。
- Core Speech Kit 负责语音识别和短回复语音合成；封装 `SpeechProvider` 接口，避免业务逻辑绑定具体实现。
- 页面“说话”按钮和文字输入统一进入同一个对话入口；耳机和热词入口后续接入时不改对话主流程。
- Telephony Kit 拉起系统电话流程。
- 本地只保存短期会话状态和待同步队列，长期记忆以云端为准。

### 后端

- Python FastAPI，接口简单、易测试。
- PostgreSQL 保存账号映射、偏好、会话、推荐快照、反馈和通话任务。
- 先使用结构化字段与事件日志，不在 V1 过早引入向量数据库。
- 服务端调用高德 Web 服务 API，密钥不放入手机 App。
- 对话模型封装为可替换的 `LLMProvider`。模型只负责意图/槽位结构化和自然语言表达，硬过滤、排序、权限与外部动作由确定性代码控制。

### 账号

- V1 使用华为账号登录，服务端把华为身份映射为 Olivia 自己的 `user_id`。
- 数据表不直接以华为账号作为主键，以便以后加入手机号、邮箱、iPhone 或 Web 登录。

### 推荐排序

先硬过滤，再固定公式打分，以保证结果稳定：

1. 硬过滤：营业状态不符、超距离、超预算、明确不喜欢的口味、关键数据严重缺失。
2. 软排序：口味匹配 35%、距离 25%、预算匹配 15%、评分稳定性 15%、历史反馈 10%。
3. 同一请求保存候选快照；用户没有改变条件时，“换一家”从快照取下一家，避免前后漂移。
4. 模型不能修改候选分数，不能补造价格、菜品、评分或评论。

## 4. 数据模型（V1 最小集合）

| 表 | 主要内容 |
|---|---|
| `users` | Olivia 用户、登录身份映射、创建时间 |
| `user_preferences` | 喜欢/不喜欢口味、预算、距离、常去区域、环境、排队、辣度、油腻、安静、娱乐类型 |
| `preference_events` | “太贵/太远/喜欢/一般”等反馈原文、结构化变化、变化前后值、可撤销标记 |
| `conversation_sessions` | 当前口味、预算、候选快照、选中餐厅、流程状态、过期时间 |
| `messages` | 用户输入、Olivia 回复、来源（语音/按钮）、意图、时间 |
| `restaurant_snapshots` | POI 原始来源、字段、查询条件、计算分数和推荐理由 |
| `call_tasks` | 商家、号码、创建/拨号/结果状态、用户记录的回答、时间线 |
| `audit_logs` | 登录、记忆修改、外部查询、拨号等可追踪动作，不保存密钥 |

每条偏好更新都保存事件，设置页允许查看、修改和恢复默认值；不能把模型的一次猜测直接写成长久偏好。

## 6. 对话状态机

```text
待命
  → 用户触发
  → 听取一句话
  → 判断意图
      ├─ 吃什么 → 缺口味？只问口味 → 查询/过滤/排序 → 候选列表
      ├─ 换口味 → 回到口味选择
      ├─ 换预算 → 只问新预算 → 重算候选
      ├─ 换一家 → 同一候选快照取下一家
      ├─ 打电话 → 必须已有选中餐厅 → 创建任务 → 拨号 → 记录结果
      ├─ 修改记忆 → 复述将修改的字段 → 写入事件 → 可撤销
      └─ 其它 → 简短说明当前 V1 能做什么
```

每轮只保留一个待回答问题。先展示可用候选，再允许继续细化；除拨号外不重复确认低风险操作。

## 7. 验收测试清单

| 类别 | 必测内容 |
|---|---|
| 安静待命 | 未触发 30 分钟不录音、不播报、不弹业务消息；检查耗电 |
| 登录同步 | 退出重登、清缓存、另一台测试设备登录后偏好一致 |
| 语音 | 安静环境/街道环境/手机麦克风；识别失败时能重试或改文字输入 |
| 对话 | 首问只有一个；换口味回退；换预算重算；换一家不重复 |
| 推荐 | 3～5 家；预算、距离、关闭状态过滤；字段缺失不编造 |
| 记忆 | 喜欢/不喜欢/太贵/太远可见、可改、可撤销 |
| 电话 | 有号码、无号码、拒绝权限、双卡、无人接、拨号失败 |
| 弱网 | 后端、模型、地图分别超时；有明确降级且不重复外部动作 |
| 可追踪 | 每次推荐和拨号可看到时间、对象、结果、失败原因 |
